In this chapter you will look into the basic rendering mechanisms, and add custom rendering to your app.

== Dev mode rendering

As you saw when setting up Next.js, each content item automatically maps to a page listing available props. These props are fetched by the Enonic adapter.

By defining custom queries and React components tailored for each content type, you can customize the props passed to the view, and which React template is actually applied.

== Media URLs

The `getPerson` query requests the image with `${imageUrlQuery({scale: 'width(500)'})}`, a Next.XP helper that selects the URL object (`path`, `queryString` and the media components) of a scaled version of the image.
Its `path` is server-relative, so the view turns it into an absolute URL pointing at XP's media API with `imageUrl(photo.imageUrl)`.
The base URL comes from `+ENONIC_MEDIA_CDN+` and defaults to `+ENONIC_API+`, so no XP configuration is needed.

Every Guillotine URL field has such a pair: `imageUrlQuery()`/`imageUrl()`, `mediaUrlQuery()`/`mediaUrl()`, `attachmentUrlQuery()`/`attachmentUrl()` and `pageUrlQuery()`/`pageUrl()`.
The `pageUrl(data, meta)` function is the one to use for links between content items: it returns a relative URL prefixed with the current locale, except for the default locale which has no prefix.

== Task: Add a custom header and footer

A header and a footer make the site more interesting visually, and Next.js layouts are a handy way of adding them.

Next.js layouts wrap every page below them. The starter has a root layout (`src/app/layout.tsx`), a locale layout and a content layout (`src/app/[locale]/[[...contentPath]]/layout.tsx`). By modifying the last one, you can inject the same header and footer components into all content pages.

TIP: Sample header and footer views are already included in the starter under `src/components/views`, so all you need to do is put them to work.

Update `src/app/[locale]/[[...contentPath]]/layout.tsx` with the following changes:

. *Add these imports*:
+
[source,typescript]
----
import Header from '../../../components/views/Header';
import Footer from '../../../components/views/Footer';
----

. *Replace the return statement* - At the bottom of the file, replace the entire return statement:
+
[source,typescript]
----
return (
    <LocaleContextProvider locale={resolvedParams.locale}>
        <StaticContent condition={isEdit}>
            <main>{children}</main>
            <DraftModeIndicator label={I18n.localize('draft-mode')}/>
        </StaticContent>
    </LocaleContextProvider>
)
----
+
With this:
+
[source,typescript]
----
return (
    <LocaleContextProvider locale={resolvedParams.locale}>
        <StaticContent condition={isEdit}>
            <Header meta={meta} title={I18n.localize('title')} logoUrl="/images/xp-logo.svg"/>
            <main>{children}</main>
            <Footer/>
            <DraftModeIndicator label={I18n.localize('draft-mode')}/>
        </StaticContent>
    </LocaleContextProvider>
)
----

. *Verify the result* - Morgan Floatman's page should now look like this:

== The common query

You may have noticed the `Common` props appearing in the various prop views. These originate from the following statement in the mappings:

.src/components/_mappings.ts
[source,typescript]
----
...

// Common query
ComponentRegistry.setCommonQuery([commonQuery, commonVariables]);

...
----

The result of this query is available across all components on the page, and may be useful if you want to fetch data for the page itself or to be used across multiple components. Feel free to adapt it to your requirements.

NOTE: If you do not need any common props, remove the common query from the mappings to optimize performance.
