In this chapter you will add configurable parts to your pages: a list of child items and, optionally, a heading.

Enonic provides a highly customizable component type called {cms-docs}/{cms-docs-version}/pages/parts[parts]. You have already created one, called `Paragraph`, in the previous chapter.
Like page components, parts must be defined in both Enonic and Next.js to fully work.

== Task: Add a part to Enonic

Start by adding a component that lists child items in the tree structure.

. *Check the part descriptor* - Verify that the Enonic app (not the Next.js front-end) has the `child-list` part descriptor at:
+
.src/main/resources/cms/parts/child-list/child-list.yaml
[source,yaml]
----
kind: "Part"
title: "Child list"
description: "Lists children of current item"
form:
  - type: "ComboBox"
    name: "sorting"
    label: "Sort order"
    occurrences:
      min: 0
      max: 1
    options:
      - value: "displayName ASC"
        label: "Ascending"
      - value: "displayName DESC"
        label: "Descending"
    default: "displayName ASC"
----
+
NOTE: This component also contains a form, similar to content types.
This means editors can configure it, sorting the items in ascending or descending order.

. *Redeploy your Enonic app* - This is only needed if you had to add the descriptor, and happens automatically if you started `enonic dev`. It makes the new part available in Content Studio.

. *Add the part to a page* - Back in Content Studio, edit the `/hmdb/persons` folder item.
Open the Context Panel (`Show Context Panel` in the top right corner), select `Page` in the widget dropdown and choose `Main` in the Template dropdown to turn the folder into a page.
Drag `Part` from the `Insert` tab into the region, then select `Child list` in the part dropdown of the `Inspect` tab.

. *Verify the result* - The part appears without any changes to the front-end. This is because the Enonic adapter contains fallback part rendering, as long as Next.js is running in dev mode.
+
image::missing-component.png[Next.js dev mode renders helpful feedback when components are missing,width=1440]

== Task: Configure part rendering in Next.js

Over in the front-end, register a new component that supports rendering of this part.

. *Add the part implementation to the Next.js app*:
+
.src/components/parts/ChildList.tsx
[source,typescript]
----
include::{sourcedir}/components/parts/ChildList.tsx[]
----

. *Register the component* - Update `+_mappings.ts+` with the following new lines:
+
.src/components/_mappings.ts
[source,typescript,options="nowrap"]
----
import ChildList, {childListProcessor, getChildList} from './parts/ChildList';

// Part mappings
ComponentRegistry.addPart(`${APP_NAME}:child-list`, {
    query: getChildList,
    processor: childListProcessor,
    view: ChildList
});
----
+
As you may have noticed, this component has a query, a view and a processor. Processors are optional JavaScript functions that can do whatever you need them to, for instance fetch data from another source than the CMS, or post-process the query response before it is passed to the view.
+
The Enonic adapter executes the query, passes the result via the processor, and then to the view which renders the component.
+
NOTE: Like macros, all page components support `configQuery`. Here though, if `configQuery` is omitted, the `config` prop falls back to the raw form values via `configAsJson`.

. *Verify the rendering* - Content Studio now shows the part with a list of persons:
+
image::child-list-rendered.png[Part rendered with list of persons as seen from Content Studio,width=1440]
+
Try customizing the part configuration and see what happens.

== Task: Add a heading part (optional)

For more components to play with, you may add another part. This task is optional.

. *Check the part descriptor* - Verify that the Enonic app (not the Next.js front-end) contains the `heading` part descriptor.
+
This part definition includes a form, with an {cms-docs}/{cms-docs-version}/schemas/form-items[form item] called `heading`. This makes it possible for editors to override the heading (the display name) coming from the content item.
+
.src/main/resources/cms/parts/heading/heading.yaml
[source,yaml]
----
kind: "Part"
title: "Heading"
description: "Demo heading"
form:
- type: "TextLine"
  name: "heading"
  label: "Override heading"
----

. *Redeploy the Enonic app* - This is only needed if you had to add the descriptor, and happens automatically if you started `enonic dev`.

. *Add the heading component in Next.js*:
+
.src/components/parts/Heading.tsx
[source,typescript]
----
include::{sourcedir}/components/parts/Heading.tsx[]
----

. *Register the part* - Add the following lines to `+_mappings.ts+`:
+
.src/components/_mappings.ts
[source,typescript,options="nowrap"]
----
import Heading from './parts/Heading';

// Part mappings
ComponentRegistry.addPart(`${APP_NAME}:heading`, {
    view: Heading
});
----

. *Verify the rendering* - Add the `Heading` part to your page in Content Studio. You now have three configurable parts to play with.

== Summary

You've registered a `ChildList` part with a query, a processor and a view, and seen how editors add and configure parts in Content Studio.
